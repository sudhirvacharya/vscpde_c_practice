# AUTOSAR / ISO 26262 — Software Safety Mechanisms (Interview Reference)

## 1. Program flow / timing monitoring

| Mechanism | What it detects | Notes |
|---|---|---|
| **Watchdog (WDT)** — window / logical watchdog | CPU lock-up, loss of program flow | Refresh should be gated on liveness of all critical tasks (bitmask/supervisor pattern), not blindly kicked from idle task |
| **Alive counter / alive supervision** | "Is this task still alive" | Task increments a counter periodically; **WdgM** checks it's incrementing within expected window |
| **Logical program flow monitoring** | Wrong branch taken / step skipped | Checkpoints (CPs) placed at expected control-flow points; sequence compared against expected graph |
| **Deadline monitoring / timeout supervision** | Task/response not completed in time window | Detects starvation, priority inversion, blocking |
| **CPU load monitoring** | Overload, starvation | Via OS timer counters or a dedicated monitor task; can feed DEM event |
| **Scheduling / timing checks** | Task exceeding allotted time budget | Complements deadline monitoring at the scheduler level |

## 2. Data integrity

| Mechanism | What it detects | Notes |
|---|---|---|
| **CRC** | Corruption in comms frames, NVM/cal data, RAM/code | Basic integrity check |
| **AUTOSAR E2E library** (Profile 1/4/5/6/7...) | Corruption, loss, delay, repetition, masquerade of signals/PDUs | = CRC + Counter + Data ID, combined; standard AUTOSAR mechanism, used in Rte/Com |
| **Checksum on RAM/ROM/Flash** | Memory content corruption | Periodic verification |
| **Redundant data storage** (dual variable / inverse storage) | Bit-flip / corruption of a stored value | Store value + its complement, compare on read |
| **Plausibility checks** | Sensor/calculated value out of physical range or rate-of-change | Range and rate limiting; cross-checks a software value against expected relationships |
| **Range checks** | Variable exceeding valid/expected bounds | Simplest form of plausibility/defensive check |

## 3. Memory & execution protection

| Mechanism | What it detects | Notes |
|---|---|---|
| **Memory Protection Unit (MPU)** | Cross-partition memory corruption | Hardware-enforced, software-configured |
| **Memory partitioning (OS-Application)** | Fault propagation between ASIL/QM software | Trusted vs non-trusted OS-Applications in AUTOSAR OS; prevents one SW component from corrupting another |
| **Stack monitoring** | Stack overflow | Canary values, stack pointer checks |
| **ECC on RAM/Flash** | Bit errors | Mostly HW, software reacts to ECC fault flags |

## 4. Control flow / redundancy

| Mechanism | What it detects | Notes |
|---|---|---|
| **Program counter monitoring** | Jump to wrong code address | |
| **Control flow monitoring** | Program executing functions out of correct sequence | Software-level counterpart to logical program flow monitoring |
| **Data flow monitoring** | Variables read/written in wrong order | Complements control flow monitoring |
| **Diverse redundancy** (N-version / dual-channel) | Systematic software faults | Two independently implemented paths, for higher ASIL |
| **Diverse software design** | Common-mode/common-bug avoidance | Same function implemented two different ways |
| **Redundant computation** | Computational faults | Same calculation run twice, results compared |
| **Comparator / voting mechanism** | Mismatch between redundant computations | Flags fault on disagreement |
| **Assertions** | Violated program invariants | Runtime check that an assumed condition actually holds |
| **Defensive programming** | Invalid/unexpected inputs | Assumes inputs may be invalid and guards against it explicitly |
| **Error / exception handling** | Runtime errors | Catches and manages faults without crashing |
| **Software watchdog trigger** | — | Periodic health-check signal sent to the hardware watchdog |

## 5. Communication

| Mechanism | What it detects | Notes |
|---|---|---|
| **E2E protection** | See above | Most commonly asked AUTOSAR-specific mechanism |
| **Bus-off recovery / comm timeout monitoring** | Bus failures, silent nodes | Handled at Com/PduR/CanSM level |

## 6. Startup / shutdown

| Mechanism | What it detects | Notes |
|---|---|---|
| **Power-on self-test (POST)** | RAM/ROM/register faults at boot | Runs before application starts |
| **Safe state transition logic** | — | On fault detection, transitions system to defined safe state (fail-silent/fail-operational) |

## AUTOSAR module mapping (quick recall)

| Mechanism | AUTOSAR module |
|---|---|
| WDT / alive / logical / deadline supervision | **WdgM** (Watchdog Manager) + **Wdg** driver |
| E2E (CRC + Counter + DataID) | **E2E library**, used within Rte/Com |
| CPU load | **Os** + custom SW-C, optionally reports to DEM |
| Memory protection | **AUTOSAR OS** (OS-Application, trusted/non-trusted) + MPU |
| Fault storage/reporting | **DEM** (Diagnostic Event Manager), escalation via **DCM** |
| Mode/safe-state management | **EcuM / BswM** |

## How this ties back to ISO 26262-6 (Table 1 / Annex D)
- WDT, alive counters, deadline monitoring → satisfy **error detection** requirements for software architectural design and support **defensive implementation techniques** (Clause 5.4.3).
- CRC, E2E, redundant storage, plausibility checks → primarily support **freedom from interference (Annex D)** and data-integrity requirements between software elements of different ASILs.
- MPU / OS-Application partitioning → the core mechanism for **freedom from interference** — prevents a lower-ASIL/QM element from corrupting a higher-ASIL one.
- Diverse redundancy / voting → used for higher ASIL (C/D) where single-channel diagnostic coverage isn't sufficient.

## Software safety lifecycle (ISO 26262-6)

```
SSR → Arch. design → Unit design/impl. → Unit test → Integration test → Safety validation
```
Software Safety Requirements are derived from the Technical Safety Concept and the hardware-software interface, then verified through structured testing.

| Metric | ASIL A | ASIL B | ASIL C | ASIL D |
|---|---|---|---|---|
| Statement coverage | highly rec. | highly rec. | highly rec. | highly rec. |
| Branch coverage | recommended (rec.) | recommended | highly rec. | highly rec. |
| MC/DC coverage | no rec. | no rec. | recommended | highly rec. |

## Freedom from interference (FFI)
- **Spatial** – no unintended memory corruption between components
- **Temporal** – no unintended timing or scheduling interference
- **Communication** – no unintended data corruption in messages

## MISRA C / coding guidelines
- Restricts unsafe or undefined C constructs
- Enforces a consistent, analyzable coding style
- Compliance checked via static analysis tools

## Important software analyses
- **SW FMEA** – bottom-up software failure modes
- **Control flow analysis** – verifies execution sequence
- **Data flow analysis** – verifies variable read/write order
- **SW FTA** – top-down, hazard to software causes

## Verification & testing methods
- Requirements-based testing
- Interface testing
- Fault injection testing
- Resource usage evaluation (stack, CPU, memory)
- Back-to-back testing (model vs. code)

## SSR & traceability
SSRs are derived top-down from the Technical Safety Concept (TSC) and allocated to software components; traceability is kept end-to-end.
- SSR ↔ architecture ↔ code ↔ test case
- Bidirectional traceability required for audits

## Key software work products
- Software safety requirements (SSR)
- Software architectural design spec
- Software unit design spec
- Software safety analysis report
- Verification report (unit / integration / safety)
- Software safety case

## Common software FuSa terms
- **SSR** – software safety requirement
- **MC/DC** – modified condition/decision coverage
- **FFI** – freedom from interference
- **SEooC** – safety element out of context

## Key takeaways
- Coverage targets rise with ASIL, especially MC/DC
- FFI matters even without hardware redundancy
- Traceability is the backbone of the safety case
- Static analysis + testing together close the gap

## Quick-fire Q&A

**Q: Name the AUTOSAR module responsible for watchdog supervision.**
A: WdgM (Watchdog Manager), on top of the Wdg driver; supports alive, deadline, and logical supervision.

**Q: What does E2E protection combine?**
A: CRC + Counter (sequence/alive) + Data ID, to detect corruption, loss, repetition, delay, and masquerading of signals.

**Q: How do you prevent a QM software component from corrupting an ASIL-D component on the same ECU?**
A: Memory partitioning via AUTOSAR OS-Applications (trusted/non-trusted) backed by an MPU — this is a freedom-from-interference mechanism per ISO 26262-6 Annex D.

**Q: Why use alive counters in addition to a watchdog?**
A: A single blind WDT refresh can't tell if a *specific* task has stalled; alive counters let WdgM confirm each monitored task individually checked in within its expected period.

**Q: What are the three dimensions of Freedom from Interference (FFI)?**
A: Spatial (no unintended memory corruption), Temporal (no unintended timing/scheduling interference), and Communication (no unintended data corruption in messages).

**Q: What's the difference between statement, branch, and MC/DC coverage requirements across ASIL levels?**
A: Statement coverage is highly recommended across all ASILs. Branch coverage becomes highly recommended from ASIL C onward. MC/DC coverage has no recommendation for ASIL A/B, is recommended for ASIL C, and highly recommended for ASIL D — reflecting the need for exhaustive condition testing at the highest safety integrity levels.

**Q: What is a SEooC?**
A: Safety Element out of Context — a safety-related element developed without a specific item integration in mind, with assumed safety requirements that must be validated when it's later integrated into an actual item.
